BAGIAN 2: ARSITEKTUR SISTEM & PEMILIHAN TEKNOLOGI (KRITERIA: STRUKTUR & ARGUMENTASI)
================================================================================
[Aksi: Tampilkan diagram arsitektur folder atau buka struktur direktori proyek di VS Code / editor]

"Bapak/Ibu dan rekan-rekan asisten, mari kita masuk ke Bagian Kedua: Fondasi Arsitektur Perangkat Lunak dan Pemilihan Teknologi.

2.1 Struktur Folder Berbasis Feature-Driven Architecture:
Dalam proyek ini, alih-alih menggunakan pendekatan 'Layer-First' konvensional yang menyatukan semua komponen di satu folder dan semua store di folder lain, saya mengadopsi pola Feature-Driven Architecture di dalam direktori `src/features/`.

Struktur dibagi menjadi 4 fitur utama:
1. `features/auth`: Mengisolasi halaman Login, Register, AuthLayout, authStore, dan authApi.
2. `features/cashflows`: Mengisolasi halaman Dashboard/HomePage, DetailPage, modal tambah dan ubah (AddModal & ChangeModal), layout navigasi, cashFlowsStore, dan cashFlowApi.
3. `features/users`: Mengisolasi Direktori Pengguna (UsersPage), halaman Profil Saya (ProfilePage), usersStore, dan userApi.
4. `features/common`: Komponen bersama seperti halaman 404 (NotFoundPage).
Serta modul penunjang di `src/helpers/` dan `src/hooks/`.

[ARGUMENTASI TEKNIS:]
Mengapa pola ini dipilih?
Alasannya adalah prinsip 'High Cohesion and Low Coupling'. Ketika fitur Cash Flow perlu dikembangkan atau di-refactor, seluruh siklus hidupnya—mulai dari komponen UI, state Pinia, endpoint API, hingga unit test-nya—berada dalam satu modul terpadu. Hal ini secara signifikan mempermudah pelacakan dependensi, memudahkan kolaborasi tim, dan meminimalkan regresi saat kode bertumbuh besar.

2.2 Pemilihan Stack & Justifikasi Teknis:
1. Nuxt (v4) dalam Mode SPA (ssr: false):
   [ARGUMENTASI TEKNIS:]
   Kami menonaktifkan Server-Side Rendering (SSR) dan mengonfigurasi `ssr: false` di file `nuxt.config.ts`. Mengapa? Delcom Cash Flow adalah aplikasi internal berbasis dashboard personal yang membutuhkan autentikasi ketat. Akses ke localStorage untuk mengambil auth token pada lingkungan server (SSR) kerap menimbulkan masalah 'hydration mismatch' dan overhead server yang tidak perlu. Dengan mode SPA, routing dan rendering sepenuhnya ditangani oleh browser klien (client-side), menghasilkan transisi halaman yang instan dan interaktif.

2. Reverse Proxy Nitro (`/delcom/**`):
   [ARGUMENTASI TEKNIS:]
   Untuk berkomunikasi dengan backend Delcom Open API (`https://open-api.delcom.org/api/v1`), kami mengonfigurasi proxy rules pada Nitro Engine di `nuxt.config.ts`:
   `routeRules: { '/delcom/**': { proxy: 'https://open-api.delcom.org/api/v1/**' } }`.
   Langkah ini sangat krusial karena menyelesaikan dua masalah fundamental sekaligus: pertama, mengeliminasi isu CORS (Cross-Origin Resource Sharing) pada sisi browser; kedua, menyembunyikan alamat backend asli sehingga meningkatkan lapisan keamanan komunikasi jaringan.

3. Tailwind CSS v4 & Lucide Icons:
   Digunakan untuk antarmuka modern, responsif, dan konsisten dengan token desain visual yang bersih tanpa membebani ukuran bundle akhir."

3.1 Modul Autentikasi Pengguna:

Pada fitur autentikasi:

- Notifikasi status menggunakan SweetAlert2 yang terbungkus rapi di dalam `toolsHelper.ts`, memberikan umpan balik visual yang elegan kepada pengguna.

3.2 Dashboard & Ringkasan Arus Kas (HomePage):
[Aksi: Buka Dashboard utama]
Halaman utama menyajikan ringkasan finansial yang komprehensif:
1. Kartu Saldo Bersih: Menghitung selisih matematis real-time antara `total_inflow` dan `total_outflow`.
2. Kartu Rincian Sumber Dana: Memecah saldo ke dalam tiga kategori dompet: Tunai (Cash), Tabungan (Savings), dan Pinjaman (Loans).
3. Filtrasi Multi-Parameter Dinamis:
   Pengguna dapat memfilter riwayat transaksi berdasarkan:
   - Pencarian kata kunci label/kategori.
   - Jenis arus kas (Pemasukan vs Pengeluaran).
   - Sumber dana (Tunai, Tabungan, Pinjaman).
   - Rentang tanggal (Start Date hingga End Date).
   [ARGUMENTASI TEKNIS:]
   Pada `HomePage.vue`, setiap perubahan filter memicu fungsi `fetchData()` yang meneruskan objek query bersih ke `cashFlowsStore.asyncGetCashFlows(filters)`. Parameter kosong atau bernilai null secara otomatis disaring di `cashFlowApi.ts` sehingga URL query string tetap bersih dan hemat bandwidth.

4. Manajemen Transaksi CRUD Lengkap:
   - Tambah Transaksi: Menggunakan modal interaktif `AddModal.vue` dengan format otomatis rupiah saat pengetikan nominal.
   - Lihat Detail: Halaman `DetailPage.vue` menyajikan breakdown status, timestamp pembuatan, dan waktu pembaruan.
   - Ubah Data: `ChangeModal.vue` memungkinkan update data transaksi yang reaktif.
   - Hapus Transaksi & Reset Semua: Dilengkapi dialog konfirmasi `showConfirmDialog()` untuk mencegah kehilangan data akibat ketidaksengajaan pengguna.

3.3 Direktori Pengguna & Manajemen Profil:
[Aksi: Buka menu Direktori Pengguna lalu Profil Saya]
- Pada halaman Direktori Pengguna (`UsersPage.vue`), kami mengimplementasikan teknik 'Client-Side Virtual Pagination' dengan mekanisme 'Muat Lebih Banyak' (Load More) per 20 entri. Ini menjaga agar DOM browser tidak terbebani saat merender ratusan pengguna sekaligus.
- Pada halaman Profil (`ProfilePage.vue`), pengguna dapat:
  1. Memperbarui informasi nama/biodata.
  2. Mengunggah foto profil (Avatar) via `FormData` multipart ke endpoint API.
  3. Mengganti kata sandi dengan validasi keamanan.

[ARGUMENTASI TEKNIS - Solusi Fallback Avatar Inovatif]:
Satu analisis menarik yang kami temukan adalah potensi kegagalan memuat URL foto profil pihak ketiga yang dapat merusak tampilan dan menimbulkan error console di audit Lighthouse.
Untuk mengatasinya, kami merancang `avatarHelper.ts`. Jika URL foto pengguna null atau gagal dimuat (`@error`), sistem secara instan menghasilkan avatar SVG berbasis Data URI di sisi klien. Warna latar belakang SVG dipilih secara deterministik menggunakan algoritma string hash DJB2 dari nama pengguna, disertai inisial huruf nama.
Solusinya: Nol network request tambahan, bebas cookie pihak ketiga, gambar selalu tajam pada resolusi layar apa pun, dan 100% bebas dari broken image error!"

BAGIAN 4: STATE MANAGEMENT PINIA & LAPISAN API (KRITERIA: ARGUMENTASI & STRUKTUR)
================================================================================
[Aksi: Tampilkan cuplikan kode `cashFlowsStore.ts` dan `apiHelper.ts`]

"Bapak/Ibu penilai, mari kita bedah logika di balik State Management dan API Layer:

4.1 Pengelolaan State dengan Pinia:
Kami memisahkan state global ke dalam tiga store independen:
1. `useAuthStore`: Mengelola status login, data token, dan prosedur logout.
2. `useCashFlowsStore`: Mengelola daftar transaksi, rincian satu transaksi, statistik kalkulasi saldo, data agregasi harian/bulanan, serta flag status asinkronus (`isCashFlowAdd`, `isCashFlowDelete`, dll.).
3. `useUsersStore`: Mengelola daftar pengguna, profil pengguna aktif (`me`), dan status mutasi profil.

[ARGUMENTASI TEKNIS:]
Mengapa pemisahan ini penting?
Dengan memisahkan store berdasarkan domain, kita menerapkan prinsip Single Responsibility. Komponen `NavbarComponent` hanya perlu memanggil `useUsersStore` untuk menampilkan nama dan foto pengguna tanpa memicu re-render yang tidak perlu dari data transaksi yang ada di `useCashFlowsStore`. Selain itu, flags seperti `isCashFlowAdd` memudahkan kita mengunci tombol (disable state) dan menampilkan indikator loading spinner selama proses simpan ke server sedang berlangsung, sehingga mencegah aksi pengiriman ganda (double-submission prevention).

4.2 Komunikasi REST API Terstandarisasi (`apiHelper.ts`):
Semua panggilan HTTP dipusatkan melalui wrapper `fetchApi(endpoint, options)`:
- Otomatis menyematkan Header `Authorization: Bearer <token>` dari localStorage jika token tersedia.
- Menetapkan `Content-Type: application/json` secara otomatis untuk request payload JSON, namun cerdas melewati header tersebut apabila payload berupa `FormData` (misalnya saat upload foto) agar browser dapat menyetel `boundary` multipart secara tepat.
- Menangkap HTTP status error (misal 401, 400, 500) dan mengekstrak pesan kesalahan server ke dalam Error exception terstruktur untuk ditangani secara konsisten oleh UI dialog."

BAGIAN 5: PENGUJIAN OTOMATIS & PIPELINE CI/CD (KRITERIA: ARGUMENTASI)
================================================================================
[Aksi: Tampilkan hasil test Vitest atau file Jenkinsfile / SonarQube properties]

"Salah satu tolok ukur profesionalisme rekayasa perangkat lunak adalah keandalan dan pengujian kode.

5.1 Unit Testing dengan Vitest & Vue Test Utils:
Seluruh komponen utama, helper, hooks, dan store di dalam proyek ini telah dilengkapi dengan berkas pengujian unit (`*.test.ts`).
- Menggunakan `vitest` dengan environment `jsdom`.
- Mengimplementasikan mock `window.localStorage`, `matchMedia`, dan mock router pada `test-utils.ts` untuk memastikan pengujian terisolasi tanpa efek samping.
- Hasil pengujian mencakup verifikasi rendering komponen, simulasi klik event, validasi transisi state Pinia, serta mock response API. Hal ini memastikan code coverage tinggi melampaui ambang batas yang disyaratkan.

5.2 Pipeline CI/CD Jenkins yang Terotomatisasi:
Sebagaimana tertera pada `Jenkinsfile`, proyek ini diintegrasikan ke dalam pipeline multi-stage:
1. Stage Checkout & Install Dependencies: Menggunakan runtime Bun alpine yang sangat cepat.
2. Stage Test: Menjalankan `npx vitest run --coverage` untuk memvalidasi seluruh test suite dan memproduksi artefak `lcov.info`.
3. Stage Trivy Security Scan: Memindai kerentanan dependensi (CVE) tingkat High dan Critical.
4. Stage SonarQube Analysis & Quality Gate: Menganalisis kebersihan kode, potensi bug, security hotspot, dan duplikasi kode melalui `sonar-scanner`.
5. Stage Package, Publish & Deploy: Mengompresi paket aplikasi bersih, mempublikasikannya, dan mengeksekusi webhook redeployment ke server staging.

[ARGUMENTASI TEKNIS:]
Penerapan pipeline ini menjamin bahwa setiap kode yang masuk ke branch utama telah terverifikasi secara fungsional, aman dari kerentanan dependensi pihak ketiga, dan memenuhi standar kode bersih (Clean Code) sebelum dideploy ke lingkungan produksi."

BAGIAN 6: OPTIMASI PERFORMA & LIGHTHOUSE AUDIT (KRITERIA: KEJELASAN)

[Aksi: Tampilkan konfigurasi optimasi pada `nuxt.config.ts`]

"Terakhir, sebelum menarik kesimpulan, kami juga melakukan serangkaian optimasi lanjutan untuk menjamin performa puncak:
1. Route-Level Code Splitting: Pada `src/routes.ts`, seluruh halaman di-load secara asinkron menggunakan dynamic import (`() => import(...)`), sehingga bundle awal saat login tetap sangat kecil dan cepat diunduh.
2. Nitro Public Assets Compression: Mengaktifkan `compressPublicAssets: true` pada `nuxt.config.ts` untuk melayani aset dengan kompresi gzip/brotli.
3. Preload & Semantic Head Elements: Memasukkan link preload untuk logo SVG, deklarasi bahasa HTML (`lang='id'`), serta meta tags deskriptif untuk skor SEO dan Best Practices maksimum.
4. Error Handling Asinkron: Membungkus pemanggilan lifecycle `onMounted` dalam blok `try-catch` terproteksi, mencegah timbulnya uncaught exception di console browser."
